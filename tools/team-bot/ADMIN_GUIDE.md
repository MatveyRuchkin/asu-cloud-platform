# Администратору

Администраторы задаются владельцем через Secret `ADMIN_TELEGRAM_IDS`. Роль руководителя в `team.json` и право подтверждать личность — разные полномочия. Выбор имени руководителя не даёт ни роль до одобрения, ни право администрирования.

## Регистрация

Откройте бот, выберите себя, затем `/pending`. Bootstrap-администратор может проверить и подтвердить свою заявку до получения роли. Остальных сверяйте по Telegram user_id через уже известный канал связи: сообщение с тем же именем не доказательство. Один участник может иметь только одну одобренную привязку; старые заявки при смене имени становятся недействительными.

После подтверждения студент включает `/settings`, если согласен получать уведомления. Администратору тоже нужно включить уведомления для автоматических заявок. Если администратор ещё не зарегистрирован, заявка хранится в D1 и видна через `/pending`, бот не заявляет об успешном уведомлении.

Список всех 18 человек и роли берутся из `site/team.json`, ветка `GITHUB_REF`. Изменения этого файла требуют обычного ревью; бот не меняет обязанности людей. При удалении/переименовании slug потребуется проверить привязки и блокеры.

## Команды

| Команда | Действие |
|---|---|
| `/pending` | До 20 заявок с проверкой личности; обрабатывайте их по очереди |
| `/disable TELEGRAM_ID` | Отключить пользователя и уведомления; `/start` не возвращает доступ |
| `/deleteuser TELEGRAM_ID` | Показать кнопку подтверждения удаления данных и связанных блокеров |
| `/critical ID_БЛОКЕРА` | Пометить критичность, позволяющую более раннюю эскалацию PM |
| `/delivery` | Последние 20 ошибок, повторов и неопределённых доставок |
| `/retrydelivery ID_УВЕДОМЛЕНИЯ` | Подтверждаемый повтор после сверки с получателем; может создать дубликат |
| `/report` | Только одобренным lead/tech_lead/project_manager; lead видит свою область |

Включить отключённого участника можно после проверки через удаление его сведений и новую одобренную регистрацию. Это намеренно не происходит автоматически.

## Блокеры и эскалация

Карточка не отправляется, пока автор не подтвердит текст и дальнейшую эскалацию. Текст содержит описание и номер Issue; история личного чата не пересылается. Направление и упоминание человека дают предположение о получателе; автор выбирает/подтверждает его. Документированная зависимость сама по себе не доказывает блокировку.

По умолчанию: через 24 часа одно напоминание ответственному, ещё через 48 часов его лиду, затем Tech Lead, затем повторная эскалация Tech Lead и только после неё PM. Для критичных карточек этап PM наступает на один шаг раньше. Если первый контакт по структуре — PM, обычный технический вопрос направляется Tech Lead. Отключённые уведомления учитываются перед фактической отправкой; недоступность адресата не скрывается.

Состояния доставки:

- `pending` / `retry`: сохранено, ожидает обработки/повтора; учитывается `retry_after` Telegram.
- `sent`: Telegram подтвердил отправку и вернул message_id. Текст удаляется из outbox.
- `unavailable`: нет одобренной регистрации, выключены уведомления или Telegram запретил отправку.
- `uncertain`: результат запроса неизвестен либо процесс прервался после начала отправки. Запись не удаляется и автоматически не пересылается.
- `rejected`: Telegram отверг запрос; проверьте конфигурацию.

Перед `/retrydelivery` узнайте у получателя, пришло ли сообщение. Telegram не имеет idempotency key для sendMessage, поэтому абсолютная гарантия однократной доставки при обрыве связи невозможна. Не воспринимайте `pending` как `sent`. Через 30 дней текст нерешённых ошибок удаляется, метаданные сохраняются.

Cron восстанавливает задания из D1 каждые 15 минут; он не зависит от сохранности сообщения в Queue дольше 24 часов. При сбоях задания имеют `available` и повторяются с задержкой. DLQ сохраняет неудачные сообщения очереди на 24 часа; исходные задания остаются в D1. Для проверки администратором через Wrangler:

```powershell
npx wrangler d1 execute asu-team-bot --remote --command "SELECT kind,status,count(*) FROM jobs GROUP BY kind,status"
npx wrangler d1 execute asu-team-bot --remote --command "SELECT status,count(*) FROM notifications GROUP BY status"
```

## Данные и резервные копии

Хранятся Telegram ID, slug, согласие, заявки, блокеры, служебные состояния доставки. Полная история чата не накапливается. Payload обновления удаляется после обработки; минимальный журнал вида обращения хранится 7 дней. `update_id` остаётся для защиты от повторов. Тексты нерешённых запросов сохраняются до обработки, черновики живут 30 минут. Публичная документация GitHub кэшируется с TTL.

Удаление пользователя удаляет привязку, заявки, черновики, журнал обращений, персональный бюджет, связанные блокеры и уведомления; входные payload очищаются. В уже полученных Telegram-сообщениях и старых резервных копиях текст может остаться. Удаляйте ненужные экспорты отдельно; Time Travel Free имеет окно до 7 дней. Удалённый участник может заново зарегистрироваться только с новым одобрением.

Экспорт и восстановление описаны в [DEPLOY_CLOUDFLARE.md](DEPLOY_CLOUDFLARE.md). Экспорт — персональные данные, храните его отдельно и защищённо. Нужны регулярная ручная/организационная процедура резервирования и проверка восстановления в новой базе. Автоматическая выгрузка в платный сервис не включена.

## Перед эксплуатацией

Проверьте `/start` → одобрение → `/settings` → `/mytask`, реальные `getMe` и `sendMessage` из Worker, один блокер двумя тестовыми участниками, отчёт, отключение/удаление, экспорт и восстановление в отдельной базе. Прогоните оценку Workers AI по трём вопросам и прочитайте ответы. Настройте read-only GitHub PAT и контролируйте Free-квоты. GitHub main/dev бот не изменяет, merge требует ревью команды.
