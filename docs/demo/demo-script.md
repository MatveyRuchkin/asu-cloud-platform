# DEMO-01 — сценарий демонстрации студенческой платформы

Задача: [Issue #19](https://github.com/MatveyRuchkin/asu-cloud-platform/issues/19). Автор сценария: Матвей Скорлыгин.

**Статус: черновик для согласования с PM Матвеем Ручкиным и UX-дизайнером Михаилом Никитиным.** Аудитория — преподаватель. Продолжительность — 4 минуты, допустимо 3–5 минут.

## 1. Что показываем и что уже готово

История: студент входит в платформу, находит полезное объявление, предлагает свою помощь и переходит к обсуждениям своего вуза на форуме.

Сценарий подготовлен 20 ноября 2026 по `dev`, коммит `f12cb6836a5bf02cf2a09df98bd4a5c28aa1896e`. В этой версии есть каркас: во frontend — `PlaceholderView.vue`, в каталогах доменных модулей backend — заготовки `__init__.py`. Готовность живого входа, объявлений и форума не подтверждена. Сейчас сценарий можно репетировать по текстовым карточкам из раздела 6. Сам каркас и ответ `/health` не доказывают готовность пользовательских действий.

Перед показом выбираем один из режимов и называем его преподавателю:

- **Живой показ:** каждый демонстрируемый шаг заранее проверен на выбранной версии платформы.
- **Показ макета:** используем согласованные экраны либо текстовые карточки ниже и говорим: «Это макет предполагаемого поведения; интеграция модулей ещё готовится».
- **Смешанный показ:** перед каждым переходом к макету явно сообщаем об этом.

Основание: [правила проекта](../../AGENTS.md), [порядок участия](../../CONTRIBUTING.md), [README](../../README.md), [требования](../requirements.md), [исходная архитектура](../architecture.md), [актуальные решения](../architecture/decisions.md), [структура и запуск](../architecture/structure.md), [OpenAPI](../api/openapi.yaml). Контракт имеет статус DRAFT. Сайт команды на GitHub Pages не является студенческой платформой.

В основной показ входят вход, просмотр и создание объявления, просмотр разделов и тем форума. Регистрацию оставляем за кадром: аккаунт готовим заранее. Личные сообщения, файлы, общеплатформенный поиск и админ-панель не входят в этот сценарий.

## 2. Первые шаги и подготовка

1. Открой Issue #19, проверь назначение исполнителя. Если задача ещё не закреплена, напиши «беру» согласно CONTRIBUTING.md.
2. Подготовь отдельную ветку `feature/19` от актуальной `dev`. Добавляем только `docs/demo/demo-script.md`.
3. С PM и UX-дизайнером выбери режим показа и согласуй названия экранов. В сценарии они описательные: точные кнопки и URL интерфейса ещё нужно сверить с реализацией.
4. Для живого режима получи у ответственных адрес демо-стенда и тестовый аккаунт. Запуск локальной версии описан в [инструкции проекта](../architecture/structure.md), [frontend README](../../frontend/README.md) и [backend README](../../backend/README.md).
5. Вместе с QA и владельцами модулей подготовь вымышленные данные из раздела 3 штатным способом. Не меняй БД, миграции или API ради демонстрации. Пароль передаётся отдельно и не попадает в этот файл, PR, запись или снимки экрана.
6. Проверь все переходы и ожидаемые результаты из раздела 4. Даже при работающем сервере непроверенный шаг показывай как макет.
7. Открой резервные материалы локально до выступления. Эти текстовые карточки доступны без сети; если есть согласованные макеты, заранее сохрани их для показа без сети. Проверь их открытие.
8. Проведи репетицию с таймером. После репетиции запиши фактические результаты по разделу 7.

Если для подготовки не хватает данных или экрана, сообщи лиду. DEMO-01 не требует самостоятельно реализовывать недостающие модули.

## 3. Короткие примеры и данные

Все имена и тексты ниже вымышленные. Это предложения для демо; наличие таких записей на стенде нужно проверить заранее.

| Объект | Пример | Что проверить перед живым показом |
| --- | --- | --- |
| Студент | «Демо-студент», `demo.student@example.org` | Аккаунт создан, вход проверен, выбран существующий демо-вуз; пароль хранится отдельно |
| Вуз | Согласованный тестовый вуз | Название и идентификатор берём из данных стенда, не придумываем UUID |
| Объявление в списке | «Отдам учебник по математике»; «Учебник для первого курса. Демо-пример» | Запись есть в выбранной категории и вузе, её текст виден в списке |
| Новое объявление | «Помогу с математикой»; «Объясню решение учебной задачи. Демо-пример»; цена 0 рублей | Выбрана существующая согласованная категория; форма и сохранение проверены |
| Раздел форума | «Учёба» | Есть в данных стенда; иначе выбираем другой согласованный раздел |
| Тема форума | «Как подготовиться к первой сессии?» | Есть в выбранном разделе и видна в списке тем |

Категории, вуз и раздел готовим до выступления. При отсутствии подходящих данных используем карточки, не создаём записи прямыми SQL-запросами. Для повторной репетиции согласуем с владельцем стенда подготовку данных; повторная публикация может создать дубликат объявления.

## 4. Основной сценарий — 4 минуты

В колонке «ожидаемый результат» описана цель шага, а не утверждение о готовности текущего каркаса. В режиме макета те же действия проговариваются по карточкам из раздела 6, без отправки запросов.

| Время | Действие демонстратора | Короткая реплика | Ожидаемый результат |
| --- | --- | --- | --- |
| 0:00–0:20 | Открыть подготовленную платформу или макет, назвать режим | «Покажу путь студента: войти, найти помощь в объявлениях и перейти к обсуждениям» | Преподавателю понятны цель и режим показа |
| 0:20–1:00 | Открыть вход, ввести email тестового аккаунта и его пароль, нажать кнопку входа. Показать имя и выбранный вуз, если это поддержано проверенным интерфейсом | «Вхожу как демо-студент. У аккаунта заранее выбран вуз» | Вход завершён; интерфейс показывает авторизованное состояние. В макете — карточка «Вход» |
| 1:00–1:40 | Перейти к объявлениям. Выбрать подготовленные фильтры категории и вуза, если они доступны в проверенной версии. Найти учебник в списке и прочитать заголовок и описание | «Здесь студент находит полезные предложения, например учебник для первого курса» | Подготовленное объявление видно в списке. В макете — первая запись карточки «Объявления» |
| 1:40–2:35 | Открыть форму объявления, выбрать готовую категорию, ввести «Помогу с математикой», описание из раздела 3 и цену 0. Отправить один раз, затем проверить запись в списке | «Теперь предложу помощь другим студентам» | Успех подтверждён интерфейсом, новое объявление видно в списке. При непроверенном сохранении — только макет второй записи |
| 2:35–3:35 | Перейти на форум, показать разделы, выбрать «Учёба» и найти тему «Как подготовиться к первой сессии?» в списке тем | «В объявлениях мы нашли предложение, а на форуме можно найти обсуждение по учебному вопросу» | Видны выбранный раздел и подготовленная тема. В макете — карточка «Форум» |
| 3:35–4:00 | Кратко повторить пройденный путь и назвать ограничения фактически показанной версии | «Мы прошли вход, объявления и форум. Показанные макеты обозначают следующие шаги разработки» | Показ завершён в срок, готовые функции и макеты различимы |

Если весь показ живой, заключительную реплику адаптировать: «Все показанные действия выполнены на демо-стенде». Эту фразу допустимо произносить только после фактического выполнения шагов.

Создание тем, ответы и чтение отдельной темы с ответами не включены в основной показ: соответствующих операций нет в прочитанном OpenAPI. Можно обсудить их как будущее развитие, но не изображать работающей функцией.

### Сверка сценария с контрактом для подготовки

Эту таблицу преподавателю показывать необязательно. Пути приведены относительно `/api/v1` и только для проверки соответствия сценарию.

| Шаг | Что описано в текущем OpenAPI | Ограничение |
| --- | --- | --- |
| Вход | `POST /auth/login`: `email`, `password`; ответ 200 — `access_token`, `token_type` | Токен не показываем и не сохраняем в документации |
| Профиль и вуз | `GET /users/me`, `GET /universities` | Отдельный экран профиля не является обязательным шагом демо |
| Список объявлений | `GET /ads`, фильтры `category_id`, `university_id` | Отдельная страница объявления не требуется |
| Создание объявления | `POST /ads`; обязательны `category_id`, `title`, `description`; необязательны `price_rub`, `image_url`; успех — 201 | В примере `price_rub` — целое 0, изображение не добавляем. Источник категорий уточняем у команды; новый API не придумываем |
| Форум | `GET /forum/sections`, `GET /forum/topics` с фильтром `section_id` | Только просмотр разделов и списка тем; операции создания и ответов не описаны |

## 5. Резервный план при сбое

Правило: одна короткая попытка проверить причину, не более 15 секунд на сбой. Затем сразу переходим к подготовленной карточке. Время берём из интервала соответствующего шага; на сцене ничего не устанавливаем и не исправляем.

Общая реплика: «Этот модуль сейчас недоступен. Покажу подготовленный макет; он иллюстрирует сценарий, но не подтверждает работу модуля».

| Сбой | Что делаем | Как продолжаем |
| --- | --- | --- |
| Не работает вход | При очевидной опечатке исправляем ввод один раз в пределах 15 секунд. Затем показываем карточку «Вход» | Последующие защищённые действия тоже показываем как макет. Доступные публичные экраны показываем живьём только если их работа и доступ заранее проверены; защиту не обходим |
| Не загружаются объявления | Показываем обе записи карточки «Объявления», проговариваем просмотр и создание | Переходим к проверенному форуму или его карточке |
| Не сохраняется объявление | Не нажимаем отправку многократно: результат первого запроса может быть неизвестен. При возможности один раз проверяем список, затем показываем карточку | Говорим, что сохранение не подтверждено. Продолжаем с форума |
| Не работает форум или список тем | Показываем карточку «Форум»: раздел и заголовок темы | Завершаем историю, не имитируем публикацию ответа |
| Нет сети, не работает стенд или сразу несколько модулей | Используем все три локальные карточки по порядку: вход → объявления → форум | Сохраняем четырёхминутный рассказ и прямо называем его показом макета |

Для тренировки сбоев достаточно условно объявить модуль недоступным и перейти к карточке. Отключать общие сервисы или менять настройки стенда не нужно. После показа записываем, на каком шаге был сбой, и передаём информацию лиду без паролей и токенов.

## 7. Как проверить результат и приложить проверку к PR

### Самостоятельная проверка документа

1. Открой Markdown Preview и прочитай сценарий по строкам таблицы: вход → объявления → форум.
2. Убедись, что у каждого шага есть действие, короткая реплика и ожидаемый результат, а примеры не требуют настоящих данных студентов.
3. Сверь таблицу API с текущим `docs/api/openapi.yaml`; проверь отсутствие новых путей, полей и обещаний операций форума, которых нет в контракте.
4. Проверь открытие относительных ссылок в репозитории и читаемость таблиц.
5. Прочитай реплики вслух с действиями или показом карточек. Засеки время; критерий — 3–5 минут. Расписание на бумаге занимает 4 минуты, но не заменяет репетицию.
6. Повтори переход к резерву отдельно для входа, объявлений, форума и полного отсутствия сети. Убедись, что карточки открываются локально, переход занимает до 15 секунд, а рассказ сохраняет порядок модулей.
7. Перед коммитом выполни `git diff --check`, а после добавления файла — `git diff --cached --check` и `git diff --cached --name-only`. В списке изменений должен быть только `docs/demo/demo-script.md`.

### Дополнительная проверка для живого показа

На согласованном стенде пройди все действия из раздела 4. После входа проверь авторизованное состояние, после создания объявления — его наличие в списке, на форуме — раздел и тему. Запиши версию стенда и результат каждого шага. Наличие кнопки или ответа `/health` не считается проверкой сценария целиком.

### Запись фактического результата

На момент подготовки этого черновика живой показ, устная репетиция и согласование с PM/UX **не выполнены**. Для PR заполни запись ниже реальными результатами; незаполненные пункты оставь как «не выполнено» с причиной.

| Проверка | Что записать в PR |
| --- | --- |
| Версия | Ветка, commit SHA, дата, выбранный режим, адрес демо-стенда при наличии |
| Документ | Проверены ли порядок, примеры, резерв, ссылки и соответствие OpenAPI; найденные замечания |
| Репетиция | Фактическое время; кто проводил; живой показ или макет |
| Живые шаги | Вход / список объявлений / создание / разделы и темы: пройдено, сбой или не выполнено; причина |
| Резерв | Результат каждой условной неисправности; время переключения; доступность карточек без сети |
| Объём изменений | Вывод проверки diff: только целевой документ; результат `git diff --cached --check` |
| Согласование | Комментарии PM и UX-дизайнера либо «ожидается» |

Изменяется только документация. Запуск приложения и тестов backend/frontend в рамках подготовки файла не выполнялся; готовность модулей этим документом не подтверждается. В PR отдельно указываем выполненные проверки документа и фактические результаты репетиции, а обязательные проверки репозитория оставляем включёнными.
