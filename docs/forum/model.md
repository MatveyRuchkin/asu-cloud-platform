# Модель форума (BE-02) — черновик для согласования

**Статус:** черновик. Документ подготовлен в рамках BE-02 («Описать структуру разделов, тем и ответов форума»).  
**Важно:** это не утверждённый контракт и не схема БД. Любые изменения `docs/api/openapi.yaml`, миграций/таблиц БД, зависимостей и общей архитектуры — только через Issue/PR и согласование с ответственными (см. `AGENTS.md`). Серверный модуль форума реализуется **только после утверждения модели и согласования контракта**.

## 1. Цель

Зафиксировать сущности форума, их связи, предлагаемые поля и ограничения, чтобы:

- согласовать идентификаторы и связи с БД и OpenAPI;
- выявить расхождения с текущим черновиком `docs/api/openapi.yaml`;
- дать основу для отдельной реализации `backend/app/modules/forum/` после утверждения.

## 2. Что уже есть в текущем черновике OpenAPI

Источник: `docs/api/openapi.yaml` (черновик, не утверждён).

### Эндпоинты
- `GET /forum/sections` — список разделов (`ForumSection[]`).
- `GET /forum/topics` — список тем (`ForumTopic[]`), query-параметр `section_id` (`uuid`, необязательный в описании параметра).

### Схемы
- **`ForumSection`**: `id` (uuid, required), `name` (string, required), `description` (string, nullable, optional).
- **`ForumTopic`**: `id` (uuid, required), `section_id` (uuid, required), `title` (string, required), `author_id` (uuid, required).

### Наблюдаемые пробелы относительно задачи BE-02
- Нет сущности «ответ» и endpoint’ов для ответов.
- У темы нет содержания/первого сообщения, дат, статусов, признаков закрепления/закрытия.
- Нет операций создания/изменения/удаления/получения по id (только списки).
- Не описана привязка форума к университету (в продукте — «университетский форум»).
- Нет пагинации, сортировки и правил доступа/ошибок, специфичных для форума.

## 3. Сущности и связи (предложение)

### 3.1. Сущности

| Сущность | Назначение | Текущий статус в OpenAPI |
| --- | --- | --- |
| Раздел форума (`ForumSection`) | Категория/раздел для группировки тем (например, «Учёба», «Общежитие»). | Есть частично. |
| Тема форума (`ForumTopic`) | Обсуждение внутри раздела, создаётся пользователем. | Есть частично. |
| Ответ форума (`ForumPost`, рабочее название) | Сообщение/ответ внутри темы. | Отсутствует, требуется описать и согласовать. |

> Название сущности ответа (`ForumPost` / `ForumReply` / `ForumAnswer`) и имена ресурсов/полей в API — предмет согласования с API-01/BE/DB.

### 3.2. Связи

- `University 1 — N ForumSection` *(предложение, требует подтверждения)*: раздел относится к университету, т.к. форум университетский.
- `ForumSection 1 — N ForumTopic`: тема принадлежит одному разделу (`ForumTopic.section_id`).
- `ForumTopic 1 — N ForumPost`: ответ принадлежит одной теме (`ForumPost.topic_id`, предложение).
- `User 1 — N ForumTopic`: автор темы (`ForumTopic.author_id`).
- `User 1 — N ForumPost`: автор ответа (`ForumPost.author_id`, предложение).

Текстовая схема:

```text
University? --< ForumSection --< ForumTopic --< ForumPost
     User -------------------------^              ^
     User ---------------------------------------'
```

### 3.3. Базовые правила целостности (предложение)

- Все идентификаторы сущностей — UUID (строка в API, тип `uuid` в контракте/БД), формат и правила — по ADR-004/006.
- Внешние ключи обязательны там, где связь обязательна (`section_id`, `topic_id`, `author_id`).
- Нельзя создать тему в несуществующем/недоступном разделе; нельзя создать ответ в несуществующей/закрытой теме (поведение при закрытии — согласовать).
- Удаление: физическое или мягкое (soft delete) — требует отдельного решения; для MVP предпочтительно явно согласованный вариант.

## 4. Предлагаемые поля и ограничения

Ниже — предложение для обсуждения. Колонки «В OpenAPI сейчас» отражают текущий черновик; «Предложение» не является изменением контракта до согласования.

### 4.1. `ForumSection` (раздел)

| Поле | Тип (API/логика) | Обяз. | Ограничения / правила | В OpenAPI сейчас |
| --- | --- | --- | --- | --- |
| `id` | string, format `uuid` | да | PK, неизменяемый | да |
| `university_id` | string, format `uuid` | вероятно да | FK на университет; ограничивает видимость разделов рамками вуза (уточнить) | нет |
| `name` | string | да | непустое, trim; рекоменд. длина 3–120; уникальность в рамках `university_id` (уточнить) | да |
| `description` | string \| null | нет | nullable; рекоменд. макс. длина 500–1000 | да (nullable) |
| `created_at` | string, format date-time (ISO 8601 UTC) | да (в ответе) | выставляется сервером | нет |
| `updated_at` | string, format date-time (ISO 8601 UTC) | нет/да | по решению команды | нет |
| `created_by` | string, format `uuid` | зависит от прав | кто может создавать разделы — открытый вопрос | нет |
| `is_active` / `is_archived` | boolean | опц. | для скрытия без удаления (если нужно) | нет |

**Вопросы:** кто создаёт/редактирует разделы (админ/модератор/seed), нужна ли сортировка (`position`), глобальные или вуз-специфичные разделы.

### 4.2. `ForumTopic` (тема)

| Поле | Тип (API/логика) | Обяз. | Ограничения / правила | В OpenAPI сейчас |
| --- | --- | --- | --- | --- |
| `id` | string, format `uuid` | да | PK, неизменяемый | да |
| `section_id` | string, format `uuid` | да | FK на раздел; тема не переносится между разделами без отдельного решения | да |
| `author_id` | string, format `uuid` | да | FK на пользователя; обычно = текущий пользователь при создании | да |
| `title` | string | да | непустое, trim; рекоменд. длина 3–200 | да |
| `body` / `content` | string | вероятно да | текст первого сообщения темы; мин. 1 символ, макс. длина согласуется (напр. 10k) | нет |
| `created_at` | string, date-time UTC | да | серверное время создания | нет |
| `updated_at` | string, date-time UTC | опц. | время последнего изменения темы/заголовка | нет |

| `is_closed` | boolean | опц. | закрытая тема: новые ответы запрещены (если входит в MVP) | нет |
| `is_pinned` | boolean | опц. | закрепление в разделе (если входит в MVP) | нет |

**Вопросы:** хранить текст темы в `ForumTopic.body` или как первый `ForumPost`; нужен ли статус модерации; можно ли редактировать/удалять тему автору.

## 5. Предлагаемые операции API (для будущего согласования)

Текущий контракт содержит только чтение списков. Для полноценного MVP-форума, вероятно, потребуются (как предмет отдельного согласования и обновления OpenAPI):

| Метод/путь (кандидат) | Назначение | Примечание |
| --- | --- | --- |
| `GET /forum/sections` | список разделов | уже есть в черновике |
| `GET /forum/topics?section_id=...` | список тем раздела | уже есть; добавить пагинацию/сортировку? |
| `GET /forum/topics/{topic_id}` | тема + детали | нет в черновике |
| `POST /forum/topics` | создать тему | нет; требует auth и схему запроса |
| `GET /forum/topics/{topic_id}/posts` | ответы темы | нет (сущность ответов не описана) |
| `POST /forum/topics/{topic_id}/posts` | создать ответ | нет; требует auth |
| `PATCH/DELETE ...` | изменение/удаление | только при необходимости и после согласования |

Формат ошибок — единый (`code`, `message`, `details`) по ADR-006. Конкретные коды/случаи (`404 topic_not_found`, запрет ответа в закрытой теме и т.д.) — согласовать в OpenAPI.

## 6. Ограничения и правила для API (сводка)

- **Именование:** JSON-поля в `snake_case`; совпадение имён/типов frontend ↔ backend ↔ контракт.
- **Идентификаторы:** UUID строкой.
- **Даты:** ISO 8601 UTC (`...Z`).
- **Пустые коллекции:** `[]`, не `null`.
- **Строки:** обязательные текстовые поля не должны принимать пустую строку после trim (конкретные min/max — согласовать).
- **Авторизация:** создание/изменение, вероятно, требует `bearerAuth`; чтение — по продуктовым правилам (уточнить).
- **Пагинация:** формат (`limit/offset` или cursor) не определён — требуется решение API-01/команды до реализации списков с большим объёмом.

## 8. Риски несовместимости

- Реализация backend до обновления/утверждения OpenAPI приведёт к расхождению контрактов.
- Несогласованная привязка к `university_id` может сломать выборки и права доступа.
- Разный выбор «тело темы в Topic vs первый Post» влияет на API, БД и UI.
- Отсутствие пагинации/сортировки в контракте усложнит фронтенд и производительность.
