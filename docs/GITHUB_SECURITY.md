# Безопасная работа с GitHub

В проекте две общие ветки: `dev` (сборка работ участников) и `main` (стабильная версия и сайт команды). Участники работают в отдельных `feature/НОМЕР` ветках.

## Что значит Write

Участник с Write может создать и отправить свою ветку напрямую в общий репозиторий. Без Write участник делает fork и отправляет PR оттуда. **Оба способа нормальные.** Права Write не требуются для выполнения Issue.

**Важно:** пока владелец не включил защиту веток в настройках GitHub, Write технически позволяет изменить `main` и `dev` напрямую. Договорённость «не пушить туда» сама по себе не обеспечивает защиту. Все участники должны использовать отдельную ветку и Pull Request.

## Кто одобряет

1. PR участника идёт в `dev`; до сдачи автор сам проверяет, что сделал, и описывает проверку.
2. Первым проверяет лид направления. Backend/API — Константин Лаврецкий, Frontend — Алексей Хапков, БД и QA — Михаил Сергеенко; остальные — согласно [структуре команды](TEAM_STRUCTURE.md).
3. Изменения архитектуры, API, миграций, Docker и CI дополнительно согласуют с Михаилом Сергеенко.
4. Перенос `dev` → `main` — отдельный PR после технической проверки. PM не обязан лично проверять код каждой задачи.

В `.github/CODEOWNERS` назначены GitHub-пользователи для критичных файлов: `@PurpleSwtr` (подтверждённые права Write) и `@MatveyRuchkin`. Их автоматически запрашивают на ревью подходящих PR, но **без branch ruleset CODEOWNERS не запрещает слияние без одобрения**.

## Что уже проверяется автоматически

- `PR conventions / conventions`: обычный PR только в `dev` и с `Closes #НОМЕР`; релиз в `main` только из ветки `dev` **этого** репозитория.
- `Repository checks / check-docs`: целостность списка участников и задач.
- `PR safety / safety`: не допускает PR в `main` из посторонней ветки/форка, запрещает добавление известных типов файлов с секретами (`.env`, `.pem`, приватные ключи) и проверяет явные токены в diff.

Это **базовые проверки**, не полноценный аудит безопасности и **не замена защите веток**. Проверки становятся обязательными для слияния только после настройки Required status checks в GitHub.

## ОБЯЗАТЕЛЬНАЯ настройка владельцем (Settings)

Подключённое к ChatGPT GitHub-приложение не имеет прав Administration на создание rulesets. Владелец репозитория должен сделать это один раз самостоятельно:

1. Откройте [Settings → Rules → Rulesets](https://github.com/MatveyRuchkin/asu-cloud-platform/settings/rules) → **New ruleset → New branch ruleset**.
2. Название, например, `Protect main and dev`. **Enforcement status: Active**.
3. В **Target branches** добавьте точные имена `main` и `dev` (или создайте по одному ruleset на каждую ветку).
4. Включите **Restrict deletions**, **Block force pushes**, **Require a pull request before merging**.
5. В параметрах PR выберите **1 required approval**, **Dismiss stale pull request approvals when new commits are pushed**, **Require review from Code Owners** и **Require conversation resolution before merging**.
6. Включите **Require status checks to pass before merging** и выберите проверки из списка, которые уже были запущены на PR: `conventions`, `check-docs`, `safety` (в интерфейсе могут отображаться вместе с названиями workflows).
7. Не добавляйте обход (bypass) для обычных участников и не разрешайте администратору обходить требования, если GitHub предлагает такой вариант. **Save changes / Create**.

**Проверка:** откройте тестовый PR в `dev`: без одобрения и успешных проверок GitHub не должен давать нажать Merge. Попробуйте push в `main`/ `dev` только в безопасной тестовой среде — **не делайте реальный прямой push ради проверки**.

### Если rulesets недоступны

Используйте [Settings → Branches → Add branch protection rule](https://github.com/MatveyRuchkin/asu-cloud-platform/settings/branches) и создайте по одному правилу для `main` и `dev`, с теми же условиями. Не включайте **Lock branch**: он сделает ветку полностью недоступной для обновлений, включая обычные слияния.

Если GitHub не позволяет установить конкретную опцию, лучше сохранить доступную часть ограничений и сообщить техлиду об оставшемся риске.
